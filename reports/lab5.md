# 实验五：并发与同步

## 实现概要

为每个进程分别维护互斥锁和信号量的 Available、Allocation、Need。请求资源前检查安全状态，拒绝会造成死锁的请求并回滚，返回 -0xdead。获取、释放、唤醒移交和线程退出同步更新状态，关闭检测时继续记账，支持重新开启。迁移跨页时间写入，检查用户权限与无效地址。本次第六、八章的 AI 实现及本地验证合计约 16 分钟（2026-11-01 20:59 至 21:15），不包含提交者此前学习耗时。

## 问答

### 主线程退出时的资源回收

需要回收每个线程的用户栈、陷阱上下文及 TID，再回收进程代码、数据、其他用户页面和页表；还要释放文件描述符、同步对象及等待队列、内核栈和 TCB。进程成为僵尸后，保留退出码及父进程回收所需的 PCB/PID，等 waitpid 后最终释放；子进程需重新交给 initproc 管理。

TCB 可能被进程线程表、就绪队列、当前处理器、定时器、互斥锁/信号量/条件变量等待队列和停止任务队列持有。就绪队列和定时器中的引用必须移除，以免已经失去用户地址空间的线程再次运行。同步队列属于本进程，随对象释放即可清理，但不能让它们留在仍可唤醒线程的位置。当前线程还在使用自己的内核栈，不能立即释放最后一个引用；本框架通过停止任务队列延迟释放。TCB 对进程采用 Weak，避免形成永久引用环。

### 两种互斥锁的区别

Mutex1 在 unlock 时先清除 locked，再唤醒一个等待者。被唤醒的线程需要循环重新竞争，其他线程可能先获得锁，因此循环检查是必要的；这种方式可能多次阻塞并导致等待者饥饿，但只要循环和状态更新正确仍能保证互斥。

Mutex2 在存在等待者时保持 locked=true，将锁直接移交给被唤醒线程，因此 lock 从阻塞返回后可以直接认为已持锁。其正确性依赖 unlock 的保留锁状态与 FIFO 唤醒逻辑配合。若将 Mutex1 的 unlock 和 Mutex2 的 lock 混用，被唤醒线程可能与抢先取得锁的线程同时进入临界区；反向混用则可能使等待者醒来后看到 locked=true，再次睡眠而无人释放。

## 设计与验证

mutex 与 semaphore 按题目允许的方式分别检测，不覆盖二者混合、waittid 或条件变量参与的所有依赖环。Need 只记录正在请求的资源，不假设线程未来的最大需求；安全检查模拟可完成线程依次释放当前持有资源。拒绝请求后删除该次 Need，实际同步对象及其等待队列不变。阻塞对象唤醒时立即移交资源计数，避免唤醒后尚未运行期间重复分配。自旋锁在真正成功获取时记账。线程退出清除其矩阵行，避免 TID 复用继承旧状态，不伪造程序未执行的 unlock/up。

检测关闭时仍记录资源操作，使持锁后再开启检测也能识别自锁。信号量允许其他线程 up，释放操作不会使调用者的 Allocation 下溢；资源数为 0 的同步信号量也保留正常的生产者唤醒语义。
